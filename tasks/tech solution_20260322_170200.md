# Pi Agent Task Runner Technical Solution

## Goal

Make Pi act as a long-running worker that:

1. polls TaskBus on a schedule
2. claims and downloads a task book
3. reads the task book and starts execution in the current Pi session
4. sends WeCom notifications when work starts, when help is needed, and when work completes
5. records completion to `memory/YYYY-MM-DD.md`
6. marks the TaskBus item as done

## Architecture

Use a two-layer design:

### 1. OS scheduler: keep-alive only

The OS scheduled task should only ensure Pi is running. It should not own business logic.

Reason:

- OS jobs can start a process, but they do not naturally inject a task book into the live Pi session context.
- Running a separate Pi process per task would fragment context and make help/notification/state handling harder.

### 2. Pi extension: business loop

Add a new extension, `task-runner`, that runs inside Pi and owns the full lifecycle:

`idle -> claim -> download -> notify_start -> execute -> help_requested? -> done -> memory -> notify_done`

## Core Design

### Persistent state

Store runner state in `.pi/task-runner/state.json`:

- current task id
- task file path
- status
- last poll time
- last error
- help requested flag

This prevents duplicate claims and allows recovery after restart.

### TaskBus integration

Use `pi.exec(...)` to run:

- `taskbus list -e daniel -s pending`
- `taskbus claim -e daniel`
- `taskbus get <id>`
- `taskbus done <id>`

Use native `fetch()` to download the task book from `fileUrl`, then save under `tasks/`.

### Execution handoff

After download, the runner sends a structured prompt to the current Pi session via `pi.sendUserMessage(...)`.

That prompt includes:

- task id
- task file path
- the full task book content
- explicit instructions to continue until complete
- instructions to request help through WeCom if blocked

### WeCom integration

Extend `wecom-bot` so it can send proactive notifications to a configured target, not only `lastContact`.

Recommended env vars:

- `WECOM_NOTIFY_CHAT_ID`
- optional `WECOM_NOTIFY_LABEL`

The task runner emits a shared `wecom:notify` event with a formatted message payload.

The WeCom extension handles actual sending.

### Completion detection

The runner watches session events and completes the task only when the task-specific execution finishes successfully.

On completion:

1. call `taskbus done <id>`
2. append a completion record to `memory/YYYY-MM-DD.md`
3. notify WeCom
4. clear local runner state

## Minimal First Implementation

1. add proactive WeCom notify support
2. add `task-runner` extension with polling and locking
3. persist state to `.pi/task-runner/state.json`
4. mark done through TaskBus
5. write completion summaries to daily memory

## Open Constraint

The runner can request help through WeCom, but automatic detection of “I am blocked” is best implemented through an explicit tool or event marker rather than fuzzy text matching. First version can support a dedicated runner tool or event for help requests.
